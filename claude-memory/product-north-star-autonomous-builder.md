tatte, 2026-09-26, correcting the drift: "I've let the conversation drift too far toward evaluating individual safeguards instead of whether they're producing that experience." The product is an autonomous software builder that improves through use. "Build me a farming RPG" should start a sustained process that plans, builds, plays/tests what it made, fixes problems, remembers useful lessons, and keeps expanding the game without destroying earlier work.

The loop, in tatte's words: **Build** (playable increments: movement, planting, harvesting, inventory, saving) · **Check** (does the increment work, do earlier features still work) · **Remember** (decisions, unfinished work, lessons from failures - across restarts) · **Improve** (fewer repeated mistakes because of those lessons) · **Continue** (the next useful increment within budget and priorities).

Lessons must be CONTEXT-KEYED: not "backslashes are bad" but which language and context made that backslash wrong, retrieved when relevant, and demonstrably avoided afterwards - otherwise the system learns a wrong blanket rule. Neural-network-driven planning/coding/lesson-proposing is fine; ordinary software enforces budgets, runs tests, restores files. Persistent memory changes behaviour without retraining; weight updates are a separate capability.

Typical-desktop operation, lower cost and less stutter are PRODUCT REQUIREMENTS to be measured on a specified desktop while it does useful work - not consequences of the controller experiment.

**Milestone (the bar):** one desktop session that builds a small playable farming game, survives a restart, adds another feature without breaking the first ones, and avoids a previously encountered mistake because of retained experience. The controller and replay rig serve this milestone; they are not substitutes for it.

**How to apply:** frame every next step against this loop and this milestone; report safeguards only as they serve it. Related: [[long-run-accuracy-north-star]], [[legasus-production-decision-2026-09-22]], [[autodiag-mechanism-first-edit-decides]], [[no-local-models-hard-rule]].

**The manager (tatte, 2026-09-26, same day):** "a plug-and-play AI manager for software, observe-first, earn-permission-to-change"; progression Observe -> Understand -> Remember (confirmed vs suspected explanations) -> Experiment (isolated copy vs original) -> Apply and monitor (adopt on agreed checks, watch, roll back). Watching is not expertise: logs count only when turned into explanations that predict failures and interventions that measurably improve outcomes; rare failures need deliberate testing. Canonical example: repeated parse failures after a kind of generated edit -> identify the escaping context -> reproduce -> test a correction -> remember the SCOPED lesson -> catch the condition BEFORE the edit reaches the working system. The repair controller is one mechanism inside the manager. Promise: "Connect Legasus to your software. It learns how it runs, finds recurring weaknesses, and makes measured, reversible improvements." Lessons carry status suspected|confirmed.
