# Prior art, read rather than recalled — five reference implementations against the Legasus mapping

Five repositories were extracted and inspected on 2026-09-29. Every claim below cites a file and, where
it matters, a line. Nothing here changes a frozen record except one appended P6 candidate (§5).

    in-toto-develop      183 files    supply-chain attestation
    marquez-main         976 files    OpenLineage metadata / lineage server
    SWE-bench-main       679 files    evaluation harness
    mini-swe-agent-main  221 files    minimal agent loop
    SWE-ReX-main          95 files    sandboxed remote execution runtime

## 1. WHAT EACH ACTUALLY SUPPLIES, AND WHAT IT DOES NOT

    in-toto        Link binds materials (artifacts USED), products (artifacts PRODUCED), byproducts,
                   command, environment - `in_toto/models/link.py:86-98`. Layout verification does
                   signature thresholds, command alignment, EXPIRY (`verify_layout_expiration`,
                   verifylib.py:260) and MATCH rules chaining one step's products to the next step's
                   materials by HASH (`verify_match_rule`, verifylib.py:645).
                   DOES NOT HAVE: revocation. Deliberately. See §2.

    marquez        JobVersion identity = digest over namespace + job name + SORTED DECLARED INPUT
                   dataset ids + sorted output ids + job location, via `UUID.nameUUIDFromBytes`
                   - `api/src/main/java/marquez/common/Utils.java:250-280`.
                   DOES NOT HAVE: any staleness concept, and NO GATING AT ALL. Greps for
                   stale/invalidate and for deny/reject/forbid across `api/src/main/java/marquez/`
                   return nothing. It records lineage; it never refuses anything.

    SWE-bench      The verdict: `f2p == 1 and p2p == 1 -> FULL`, and the two halves are NAMED
                   "Resolution" and "Maintenance" - `swebench/harness/grading.py:309-327`.
                   DOES NOT HAVE: a runtime gate. It grades offline, after the fact.

    mini-swe-agent A 190-line agent loop (`src/minisweagent/agents/default.py`). Its only hard limits
                   are `step_limit`, `cost_limit`, `wall_time_limit_seconds` (default.py:126-145).
                   DOES NOT HAVE: authority, preservation or governance of any kind. The only greps
                   matching those words are two incidental uses of "preserving" in comments about
                   partial output and UI scroll position.

    SWE-ReX        "a runtime interface for interacting with sandboxed shell environments" (README).
                   The execution substrate. No assurance semantics.

**The structural observation across all five:** two supply the untrusted generator and its substrate;
three supply assurance. **None of the three assurance systems gates a running product.** in-toto
verifies after the fact, marquez only records, SWE-bench grades offline. That is consistent with the
stated hypothesis rather than a discovery of mine, and it is the one place the mapping understates the
difference: the pieces exist, and none of them is a *runtime* enforcement boundary over an effect that
has not yet been allowed to survive.

## 2. IN-TOTO DELIBERATELY HAS NO REVOCATION, AND SAYS WHY

`in_toto/verifylib.py:1512-1522`, in the verification entry point's own docstring:

> in-toto's verification workflow directly uses the key for verifying signatures. It does not
> communicate with external sources of information for specific attributes about keys. This ensures
> that verification can be performed **in isolation**. ... in-toto does not rely on the creation time,
> **revocation status**, and usage flags for PGP keys. **To revoke or otherwise affect the usage of a
> key, the supply chain owner must sign a new layout with the corresponding changes.**

So a mature, audited supply-chain assurance system answers "how does authorization stop being valid"
with **expiry plus re-issuance**, and rejects revocation lookup *because* it would make verification
depend on something outside the artifact being verified.

That is a candidate the P6 freeze did not enumerate, and it is the one an existing system chose. See §5.

## 3. MARQUEZ INDEPENDENTLY CORROBORATES THE DECLARED-INPUT-SET RULE

The owner's third control for candidate (b), stated before this reading: *"for ancestry, use a declared
tree/input-set digest — not `workspaceStamp()` — because speculative validity is about the exact files
the verifier observed."*

Marquez computes version identity from the **declared input and output set** — names and identifiers,
sorted — and not from a content-of-everything fingerprint. The production lineage system does exactly
what the control specifies, which is external corroboration for the ownership rule posted to COORD
(`124b0f21`) rather than a new finding.

Worth noting precisely what it is NOT: marquez's digest is over *declared identifiers*, so it changes
when the declared input set changes and not when the bytes of an input change. It is an identity for
"which job, over which inputs", not a freshness check. Legasus should not read it as evidence that a
declared-set digest can do a content check's job.

## 4. SWE-BENCH ALREADY SPLIT THE VACUITY QUESTION, ASYMMETRICALLY

`grading.py` carries three predicates, and the asymmetry is deliberate and documented:

    test_passed(case, sm)        PASSED or XFAIL                                    (grading.py:85)
    test_maintained(case, sm)    """P2P semantics: a skipped test is not a
                                 regression, unlike for F2P."""
                                 -> passed OR SKIPPED                              (grading.py:93)
    test_failed(case, sm)        no key, or FAILED / ERROR / SKIPPED, with:
                                 "# a skipped F2P test is not a resolution; without
                                  this, a patch that makes every F2P test skip lands
                                  in neither list and scores RESOLVED_FULL"         (grading.py:101)

So **skip is strict for resolution and lenient for maintenance**, and the comment records the exact
vacuity that forced the strict half: a patch that skipped every fail-to-pass test scored RESOLVED_FULL.
That is the same class of defect this project has hunted repeatedly, found and fixed in a standard
benchmark, with a written reason.

Two things follow for Legasus, and they point in opposite directions.

**(a) The residue is asymmetric, by choice.** Because `test_maintained` counts SKIPPED as maintained,
a change that makes every pass-to-pass test *skip* still scores maintenance = 1. You cannot fake
resolution by skipping; you can fake maintenance by skipping. That is a defensible choice - skips are
usually environmental rather than semantic - and it is a live residue in the code as read, not a
criticism of the design.

**(b) Legasus's preservation predicate makes no such distinction at all.** `lostDefs` and `defCounts`
are structural: a symbol that disappears is a loss regardless of whether anything depended on it, and
there is no representation of "this check no longer applies" as distinct from "this behaviour
regressed". SWE-bench's Resolution/Maintenance split is behavioural and is exactly the axis Legasus's
step-1 finding identified as unreachable - the 7 of 16 BEHAVIOUR_CHANGED cases that no symbol-level
check can see.

**And "build forward without breaking what came before" already exists as an operational verdict.**
`f2p == 1 and p2p == 1 -> FULL` is that sentence, in a benchmark, with the halves named. Legasus's
version differs in being a *runtime gate on whether bytes survive* rather than an offline grade, which
is the same distinction as §1.

## 5. THE ONE ACTIONABLE ITEM

P6's candidate list gains an eighth meaning of "invalid", appended to the frozen document as
Amendment 2 and attributed to in-toto rather than invented here:

    (f) SUPERSESSION    the authorization was replaced by a newer authorization. No revocation lookup,
                        no external state consulted at verification time; the old authorization simply
                        is not the current one. in-toto's actual answer, chosen so that verification
                        stays performable in isolation.

This is not adopted. It is enumerated, like the other seven, and it is the only one of the eight known
to be load-bearing in a system that has been audited in the field.

## 6. WHAT THIS READING DOES NOT ESTABLISH

- **Not that Legasus's combination is novel.** Runtime assurance, supply-chain attestation, lineage and
  merge gating each supply a part, which the mapping already said. What I measured is narrower: the
  three assurance systems here do not gate a running product, and two of them explicitly decline to.
- **Not that any of these would work in Legasus.** No integration was attempted and none is proposed.
- **Nothing about NASA runtime assurance, Kubernetes reconciliation, Zuul, or SLSA.** Those were
  described in the framing; no artifact for them was supplied and I read none, so I have no measurement
  and make no claim about them.
- **Nothing about the fuzzing line.** No fuzzing corpus was supplied here.
- **Not a readiness judgement.** TEST-(-1) belongs to another session (`1cf2381e`) and nothing here
  bears on its sequencing.
