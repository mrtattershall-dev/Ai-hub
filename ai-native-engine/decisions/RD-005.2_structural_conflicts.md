# RD-005.2: Structural Conflicts (Closed)

**Question:** RD-005 covered scalar/set fields. Do the same "detect, don't silently resolve" guarantees extend to *tree structure* — reparenting, child insertion, deletion of a parent, and merges that would create a cycle?

**Method:** A structural 3-way merge (tree = the parent function; children derived from parent pointers) run against four scenarios. `experiments/010_structural_conflicts/structural_conflicts.js`. All pass; each scenario hand-traced to confirm the pass is real, not accidental.

## Proven (measured)
- **S1 concurrent reparent to different parents** → surfaced as a `parent`-field conflict (both candidate parents retained), not silently picked. (Same rule as RD-005's flat same-field clash, applied to the structural `parent` field.)
- **S2 disjoint child additions** to the same container → **union**: both new children kept, no conflict. (Children behave like a set under RD-005's `set` semantics.)
- **S3 reparent to a parent the other branch deleted** → **orphan surfaced** (`{id, missingParent}`), never silently dropped or silently re-homed. Ties directly to RD-004.6 (a reference — here a parent pointer — to a deleted object must fail loudly).
- **S4 each branch nests the other's node** (X→Y, Y→X) → the merge would create a **cycle**; detected and flagged, not committed.

## Decision
Structural merges are governed by the **same detect-don't-resolve rule as RD-005**, plus two structural invariants the merge must enforce before commit:
1. **Acyclicity** — a merge that would introduce a cycle is rejected, not committed.
2. **No silent orphan** — a parent pointer to a deleted/absent node is surfaced (reuse RD-004.6 tombstone/explicit-absence), never silently dropped or re-homed.
Field-level rules carry over: `parent` is a label-like field (no fold → concurrent divergent reparent = conflict → defer); a container's child membership is a set (disjoint adds → union).

## Transferable principle
Structure is just more fields with invariants attached. The scalar rules still apply (fold where a fold exists, defer where it doesn't); trees only add two global constraints — stay acyclic, no dangling parent — that must be checked on the *merged* result, not the branches.

## Open / out of scope
- **Ordered** lists where position matters (reorder-vs-reorder) — only set-like unordered children were tested. Concurrent reorders likely need defer or an explicit ordering CRDT.
- Move + edit of the same subtree simultaneously; deep subtree moves — untested.
- No integration with the reconstructed pipeline yet.
