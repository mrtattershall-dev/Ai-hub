# RD-005.1: Where Per-Field Fold Semantics Live (Closed)

**Question:** RD-005 selects conflict resolution by a field's semantics. Where is that declaration stored — a global schema, or per-component metadata?

**Method:** Two schema designs run against properties. Falsifiable difference: two component types legitimately reuse a field name with *different* semantics. `experiments/009_fold_semantics_location/fold_semantics_location.js`.

**Candidates:** GlobalFlat (`fieldName -> semantics`), ComponentScoped (`componentType.fieldName -> semantics`, each component declares its own).

## Proven (measured)
- **GlobalFlat is INADMISSIBLE.** With `enemy.level = max` and `skill.level = additive`, the flat namespace collapses both to one entry — `enemy.level` silently resolves as `additive`. A single flat field namespace cannot represent per-type semantics, and the clobber is silent.
- **ComponentScoped passes all properties** — namespace-safe (keys by `type.field`), same-type consistent, undeclared fields default to `defer` (never guesses), and a new component **self-registers** without editing any central map.

## Decision
Per-field fold semantics live in **component metadata, keyed by `componentType.fieldName`**, not a global flat schema. Each component owns and declares its fields' merge semantics locally; the resolver looks them up by type+field. An undeclared field falls back to `defer` (RD-005's safe default). No central registry to bottleneck or merge-conflict on.

## Transferable principle
Semantics that vary by type must be namespaced by type. A global flat map of field names is a collision waiting to happen, and the collision is silent. Co-locate the rule with the thing it describes.

## Open / out of scope
- Format of the metadata (decorators / plain declaration table / schema file) — not decided, only its *location and scoping* are.
- Inheritance/override when components compose — untested.
