# RD-019.1: Tombstone GC (Closed) — bounding the RD-019 open cost

**Question:** RD-019 flagged an honest cost: snapshot size (and live memory) grows with **all-time deletions**, because RD-004.6 keeps a tombstone for every deleted uuid forever. When is a tombstone safe to drop?

## Method
Three policies, measured. `core/engine.js` `gcTombstones()`, `core/tombstone_gc_test.js` (18 assertions, ALL PASS).

- **NEVER** — keep every tombstone forever (RD-019 baseline; unbounded).
- **EAGER** — drop at delete time = HardDelete, no tombstone at all (RD-004.6's already-rejected extreme).
- **REFCNT** — drop a tombstone iff **no live entity references its uuid** — via a `refs[]` edge OR a dangling parent pointer (an orphaned child still pointing at a deleted parent).

## Proven (measured)
- **Corruption-safety is unconditional (S3).** Because uuids are NEVER recycled (RD-004.6), dropping a tombstone can never cause a wrong-live resolve: a later reference to a dropped uuid resolves `missing`, and a fresh spawn gets a new id (`u1`, never the dropped `u0`). GC cannot reintroduce the freelist bug.
- **REFCNT keeps metadata exactly while it is useful (S1/S4/S6).** A tombstone with a live referrer (by `refs` or by a dangling parent edge) is KEPT, so `resolve` still returns `deleted` + type + last-known name — precisely when a UI/migration would want to explain the dangling reference. EAGER/HardDelete would already report `missing` in that window, losing the distinction while something still points at the object.
- **REFCNT bounds storage (S2/S5).** Under a 100× create-then-delete churn with no lingering references, NEVER keeps all 100 tombstones; REFCNT reclaims all 100. When the last referrer of a kept tombstone is itself removed, the tombstone becomes droppable on the next GC (S2). Idempotent.
- **Degradation is honest (S2).** A reference to a dropped tombstone resolves `missing` (detectable absence), never a value and never a wrong object — the RD-004.6 "loud, local failure" guarantee holds, just with less metadata.
- **Composes (S7).** GC touches only the tombstone map, so indexes stay consistent (RD-017) and the smaller tombstone set round-trips through save/load (RD-019).

## Decision
- **Reference-counted tombstone GC.** A tombstone is safe to drop iff no live entity references its uuid (`refs[]` or a dangling parent pointer). Run periodically (e.g. at save-time compaction); it is O(live entities), like the RD-019 index rebuild.
- **NEVER is rejected** (unbounded growth = the RD-019 cost). **EAGER/HardDelete is rejected** (drops the `deleted`-vs-`missing` metadata while it is still reachable and useful — RD-004.6's original finding, re-confirmed).
- REFCNT is the middle path RD-004.6 implied but did not build: tombstone *by default*, reclaimed *once unreachable*.

## Transferable principle
A tombstone earns its keep only while something can still trip over the grave. Track reachability, keep the marker exactly that long, then reclaim — and because identity is never recycled, reclaiming is always safe, only ever less informative.

## What remains open
- **In-world reachability only.** GC counts references inside THIS world. A reference held by an external artifact (a save from another session, a quest log elsewhere) cannot be seen, so a dropped tombstone degrades that external ref from `deleted` to `missing`. Acceptable (still safe, ids never recycle), but a cross-session GC would need an external-reference registry or a "retain" flag — unbuilt.
- **Incremental refcount.** The O(live) sweep is fine for save-time compaction; a live per-tombstone refcount maintained on ref/parent writes would make GC O(dropped) but adds bookkeeping to the hot path — not measured to be worth it yet.
- **GC + undo interaction — checked, safe.** GC of a tombstone whose delete is still on the undo stack is fine: `undo` of a delete (`restore`) sets `destroyed=0` + `byUuid` and *deletes* the tombstone entry (a no-op if GC already removed it) — it never *reads* it, and the row data is never cleared. Verified: delete → GC (drops tombstone) → undo resurrects the entity with name + indexes intact. (A tombstone kept only because *its own* pending-undo delete referenced something is not a case that arises — GC counts live-entity references, and a pending delete's target is not live.)
