# RD-005.3: Ordered-List Conflicts (Closed) — the gap RD-005.2 left open

**Question:** RD-005.2 resolved structural conflicts only for UNORDERED (set-like) children (disjoint child-adds union; reparent-divergence defers; acyclicity + no-orphan enforced). It explicitly punted on ORDERED children — **concurrent reorders**. How should two players' simultaneous reorderings of one list merge?

**Anchoring scenario (the ordered analogue of Crop #142):** list `[A,B,C,D]`; P1 moves D to the front, P2 moves A to the end, same tick, each acting on the base. What is the merged order?

## Method
Three rival policies, measured against four properties: **determinism** (both arrival orders converge), **integrity** (no item dropped/duplicated), **intent preservation** (both players' moves survive), **minimal blocking** (defer only genuine conflicts). `experiments/021_ordered_list_conflicts/ordered_list_conflicts.js`, zero deps, 15/15 assertions PASS (each policy asserted against its *predicted* behaviour, so ALL PASS = the theory held).

- **LWW (steelman):** the winning editor's whole reorder wins, chosen by a deterministic actor-id tiebreak (not arrival order — raw arrival-order LWW doesn't even converge, which is the bare Crop #142 bug). So this is the *strongest* LWW: it converges and still discards one player's move.
- **DEFER-all:** any concurrent reorder is surfaced, base kept.
- **ORDER-KEY:** each item carries a fractional order key; the visible list is items sorted by key. A move assigns a new key between neighbours. Moves of DIFFERENT items are disjoint key-writes → union, lossless, commutative. Moves of the SAME item to different keys are a true conflict → defer that item (keep its base key), surface it.

## Proven (measured)
- **LWW converges but SILENTLY LOSES intent.** For the disjoint case it drops P1's D-to-front entirely (result `B C D A` — only P2's move survives). Integrity holds; intent does not. This is Crop #142 in list form: a valid, consistent, *wrong* result that discards a contribution.
- **DEFER-all is safe but OVER-BLOCKS.** It surfaces the disjoint P1/P2 case as a conflict even though a clean lossless merge existed — it would force the author to resolve a non-conflict.
- **ORDER-KEY satisfies all four.** Disjoint moves merge losslessly and commute → `D B C A` (D first *and* A last: both intents preserved), deterministic across all interleavings (verified over 4 permutations of a 3-actor stress), every item exactly once. And when both players move the **same** item to different slots, it defers *only that item* (keeps C at base, surfaces the clash) — exactly RD-005's resolve-where-lossless / defer-the-true-clash philosophy, now applied to order.

## Decision
- **Ordered children use fractional order-keys.** Concurrent moves of different items merge (disjoint key-writes, commutative, lossless); a concurrent move of the *same* item to different positions defers that one item and surfaces it. LWW is rejected (loses intent); blanket-defer is rejected (blocks lossless merges).
- This is the same rule as RD-005/005.2 — **fold/merge where a lossless combination exists, defer only the genuine clash** — with the "foldable field" being an item's order-key and "disjoint" meaning different items.

## Transferable principle
Order is not a single opaque value to arbitrate (LWW) nor an all-or-nothing structure to lock (blanket defer); it is a set of per-item positions that mostly compose. Give each item an independent, densely-splittable position key and concurrent reorders that don't touch the same item just merge. Reserve deferral for the real disagreement — one item, two destinations.

## What remains open
- **Interleaving of multi-element runs at one gap** — the classic fractional-index / list-CRDT wart: two actors each concurrently insert a *run* of items into the same gap can interleave. This card handled single-item moves (tie broken deterministically by actor); multi-element interleaving is flagged, not solved.
- **Key precision exhaustion** — repeated splits of the same gap shrink the fractional interval; a production system needs periodic re-keying (rebalance) or an arbitrary-precision / string-based order key (e.g. LexoRank-style). Untested.
- ~~**Integration into the core**~~ — **DONE.** `engine.js` now has an `orderKey` Float64 column, `orderedChildren(uuid)` view, and a `move{target, after}` op normalized into an `orderKey` field-write. Because order is modelled as a *field*, the whole RD-005.3 policy fell out of the existing machinery for free: different-item moves merge and same-item moves defer (undeclared field => defer semantics), and it inherits RD-017 staging, RD-020 undo/redo, RD-019 persistence, and the RD-018 protocol wire (a `move` verb). `core/ordered_test.js` 20/20 PASS. Remaining open below are refinements, not gaps.
