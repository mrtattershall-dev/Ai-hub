# RD-001.1: Index Representation at Scale (Closed) — measure-first, don't port

**Question:** RD-001 chose derived indexes (byType, childrenOf, referrersOf), implemented in the core as `Map<int, Set<int>>`. The open card asked whether to PORT them to typed-array / CSR (compressed-sparse-row) form for the 50k-entity SoA capstone. Project rule: measure before rewriting working, asymptotically-optimal code.

## Method
Both representations built from identical synthetic data at N=50,000 (~143k edges), measured on the three axes that decide it. `experiments/022_index_representation/index_representation.js`, deterministic data, run with `node --expose-gc`. Honesty (RD-008 discipline): CSR byte sizes EXACT; Map/Set memory a gc-cleaned heapUsed delta (SOFT); timings wall-clock, median of 5, SOFT — stable across runs.

## Measured (N=50k, ~143k edges)

| Axis | Map/Set (core today) | CSR typed-array | Winner |
|---|---|---|---|
| **Memory** | ~10.8 MB (~79 B/edge, soft) | **0.93 MB EXACT (6.8 B/edge)** | CSR ~11.6× smaller |
| **Read** (iterate small results) | ~46 ms / 600k q (~13 M q/s) | **~12 ms (~40 M q/s)** | CSR ~3.4× faster |
| **Incremental update** (mutate) | **~2.3 ms / 40k edge add+del (O(1)/edge, ~60 ns)** | ~4 ms per FULL rebuild — the floor cost of ANY single-edge change | Map/Set decisively |

## Decision
**KEEP `Map<int,Set<int>>` in the core. Do not port.** The read/write ratio decides it:
- The engine **mutates every commit** (RD-002/003/017). Map/Set updates in O(1)/edge — exactly that access pattern. CSR is static: any single-edge change forces an O(N) rebuild (~4 ms here) or a much more complex delta-CSR. That trade is unacceptable for interactive, transactional editing.
- CSR's real wins — ~11× memory, ~3.4× read — **do not bind at 50k**: 10.8 MB is a few MB, not a wall, and both representations exceed 10 M queries/s, so relationship reads are nowhere near the bottleneck.

**Revisit only if** (a) N grows ~10× *and* memory actually bites (~110 MB at 500k), or (b) a read-mostly / serialized-snapshot view is needed. In those cases the answer is a **derived CSR read-cache built from the Map/Set** (the RD-007 "on-disk/analysis form ≠ live form" split, applied to indexes) — augment, don't replace.

## Measurement-fragility note (RD-008 lesson, recurring — recorded honestly)
The read comparison was WRONG twice before it was right:
1. First pass measured `.size`/`.length` only (O(1) lookup, no iteration) → CSR looked ~1.0× (no advantage) — too kind to Map/Set.
2. Second pass iterated but called `.subarray()` per query, allocating a view object 400k times → CSR looked ~30–60× *slower* — a pure allocation artifact, too cruel to CSR.
3. Only allocation-free flat-array iteration (index into `values` by offset) is honest → CSR ~3.4× faster.
Same discipline as RD-008/RD-007: distrust a clean (or shocking) result until the harness itself is checked. Exact byte counts are trustworthy; anything riding on allocation/GC/heapUsed is soft and must be labelled.

## Transferable principle
A read-optimal static layout and a write-optimal mutable one are different tools; pick by the read/write ratio of the actual workload, not by which looks faster in isolation. A transactional engine that changes state every commit wants the mutable structure and can derive the packed one on demand — never the reverse.

## Validated at scale (Modal, N = 10k … 5M) — the decision holds, now quantified
Ran the ACTUAL Node experiment across a 500× N sweep on Modal high-RAM CPU containers (`experiments/022_index_representation/modal_sweep.py`, `sweep.js`; results `sweep_results.json`, plot `scaling_plots.png`). Every axis behaved as the 50k measurement predicted, and the crossovers are now concrete:

| N | Map/Set mem | CSR mem | ratio | Map read | CSR read | Map update (40k ops) | CSR rebuild |
|---|---|---|---|---|---|---|---|
| 10k | 1.9 MB | 0.19 MB | 10.4× | 32 ms | *146 ms\** | 9 ms | 1 ms |
| 100k | 17 MB | 1.9 MB | 9.3× | 38 ms | 45 ms | 11 ms | 14 ms |
| 500k | 96 MB | 9.3 MB | 10.4× | 46 ms | 31 ms | 8 ms | 57 ms |
| 1M | 178 MB | 19 MB | 9.6× | 99 ms | 37 ms | 16 ms | 96 ms |
| 5M | **868 MB** | 93 MB | 9.4× | 108 ms | **28 ms** | **12 ms** | **294 ms** |

*\* 10k CSR read is a cold-JIT outlier (that container ran first); every warm CSR read is 27–47 ms.*

- **Memory** grows linearly, Map/Set steady ~9–11× larger. The RD-001.1 prediction "~110 MB at 500k" landed at an actual **101 MB**. At 5M, Map/Set indexes cost **~870 MB** — a real budget item, exactly the "revisit if memory bites" regime.
- **Read**: CSR is **flat (~28 ms)** as N grows; Map/Set **degrades** (32→113 ms) as the scattered Sets fall out of cache. Below ~100k they are comparable (Map/Set even wins at 10–50k); above ~500k CSR pulls clearly ahead, **~3.9× at 5M**. The read advantage is a large-N, cache-locality effect.
- **Update (decisive)**: Map/Set is **flat** (~12 ms for 40k O(1) edge ops, N-independent); CSR rebuild is **linear**, reaching **294 ms per mutation at 5M**. A transactional engine that touches an index every commit cannot pay a 294 ms rebuild — this is the axis that keeps Map/Set in the core, and the gap only widens with N.

**Conclusion unchanged, now evidence-backed:** keep Map/Set for the mutable transactional core at every scale tested. The derived-CSR read-cache becomes worth building **specifically at ≥1M entities for read-heavy / analysis / snapshot passes**, where CSR's ~10× memory and ~3–4× read wins are real and Map/Set's write advantage is irrelevant (no mutation on that path).

## Robustness — how soft ARE the soft numbers? (Modal, 72 independent fresh-V8 samples @ N=50k)
`modal_robustness.py` + `plot_robustness.py`, plot `robustness_plots.png`. Coefficient of variation (std/mean) across 72 fresh processes:

| metric | CV | reading |
|---|---|---|
| CSR memory (byteLength) | **0.0%** | exact — control, identical every run |
| Map/Set memory (heapUsed) | **0.3%** | 11.29 MB ± 0.03 — the "soft" heapUsed number is actually **rock-solid** |
| Map/Set read | 28.8% | genuinely noisy (30→108 ms) |
| CSR read | 17.0% | noisy |
| Map/Set update | 18.7% | noisy |
| CSR rebuild | 24.6% | noisy |

**Finding:** the MEMORY conclusions — the backbone of this decision and of RD-008 — are trustworthy to <0.5%; the RD-008 caution about heapUsed *noise* was overcautious for the memory *magnitude* (the RD-008 ratio wobble came from the naive-baseline object *shape*, not measurement imprecision). The WALL-CLOCK timings are the real soft numbers (CV 17–29%) — which is exactly why the decision rests on memory + the O(N)-vs-O(1) asymptotic shape (both robust) and treats the read/rebuild millisecond figures as trends, not precise values. Retroactively validates the methodology used throughout.

## What remains open
- The derived-CSR read-cache (for a query-heavy AI-analysis pass or a compact on-disk index) is designed-not-built; the sweep now says it's worth it at ≥1M entities on a read-mostly path.
- Node 18 (Modal) vs Node 24 (local) gave the same shapes; the absolute read numbers are hardware/runtime-dependent (soft), the trends are robust.
