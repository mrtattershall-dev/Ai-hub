# v1.2 — who owns the semantics of an inference rule? Frozen 2026-09-21, before implementation.

## The current gap, quoted from the code that has it

`adapter.mjs`, as committed at `44aaafd`:

```js
rule: { name: 'certificate:' + cert.provenance.run_id + ':alternative' + altIndex, requires: [] },
```

`derive()` computes missing witnesses from `rule.requires || []` and refuses when any are absent. With
an empty list **no witness is ever required**, so the check passes vacuously. The calculus is behaving
correctly relative to the rule object it was handed. **The defect entered before the calculus.**

## The repair that would NOT be a repair

Letting the certificate carry `requires: [...]` lets the producer choose the burden of its own
inference:

    real rule requires   [MEMBERSHIP, REACHABILITY]
    certificate says     requires: []
    derive()             nothing missing -> mint

That is self-authored obligation with extra steps.

## The rule, frozen

> **A certificate carries rule IDENTITY, never rule AUTHORITY.** It may say *which* rule it claims to
> have used and *which witnesses it established*. It may never say what that rule requires.

    certificate      rule_id, rule_digest, relation_witnesses[]      identity + established facts
    runtime          ADMITTED_RULES[rule_id] -> { name, requires }   the obligation
    derive()         refuses on the LOCAL requires

Identical names are not identical referents — the justification graph already learned that a name
collision is not an admission — so `rule_digest` pins the definition and a mismatch is refused.

## The four arms

    R1  known rule, every required witness supplied            -> MINT
    R2  same rule, one required witness omitted                -> REFUSE
    R3  same rule_id, certificate declares its own requirement -> REFUSED or IGNORED; never honoured
    R4  a rule that genuinely requires no witness              -> MINT without witnesses

**R3 is the attack.** If a certificate can shrink its own obligation, v1.2 has recreated the defect.
**R4 is the anti-refusal control.** Without it the safe-looking repair becomes "every derivation must
carry a witness", which is a refusal machine.

**R5 DRIFT.** A certificate naming `rule X @ digest A` against a runtime holding `rule X @ digest B`
must yield `RULE_DEFINITION_MOVED`, never silent use of B. A certificate must not stay syntactically
valid while the meaning of its derivation changes underneath it. Asymmetric validity again.

## A consequence I expect and am not going to hide

F4 is admitted today through the vacuous check. Under v1.2 its rule genuinely requires a witness, so
**F4 will REFUSE until the producer emits one**. That is the correct outcome and it proves the current
admission was resting on nothing. The producer may then supply a `COVERAGE` witness because its
obligation record already establishes exhaustive coverage — supplying a **fact it established**, not a
requirement it invented.

FALSIFIER of the whole repair: F4 continues to mint without any witness.

## Predictions

    P-1  before the repair, a rule requiring MEMBERSHIP mints with zero witnesses (baseline defect)
    P-2  R1 mints, R2 refuses naming the missing relation, R3 never honours a certificate-supplied
         requirement, R4 mints with no witnesses
    P-3  R5 refuses with RULE_DEFINITION_MOVED and does not fall back to the local definition
    P-4  the v1.2 schema REFUSES any certificate carrying a `requires` field anywhere
    P-5  after the producer supplies the witness it established, F4 is admitted again, and the
         integration suite's ablation still holds unchanged

## Rules

v1.0.0 and v1.1 schemas are preserved unmodified. The adapter resolves rules locally and never reads a
requirement from certificate data. No `delegate`, no `commit`. No merge.
