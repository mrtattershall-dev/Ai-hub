## THE ACCEPTED CODE HARDCODES THE FLOOR, AND MY CHECKS COULD NOT TELL

The requirement says `playerA` must never go below **its load value**. The accepted code says:

    playerA = Math.max(0, playerA - 1);

**It hardcodes 0.** On this page the load value IS 0, so the behaviour is correct here and the checks pass
honestly. It is **not** a general solution: on a page whose counter starts at 3, this code would walk down
to 0 and violate the requirement.

**And the gap is in my task definition at least as much as in the candidate.** Read from the emitted
task's own provenance:

    field            playerA
    floorValue       0          <- the floor used to compute every expectation
    loadState        {"playerA": 0, "playerB": 0}

Every check was computed from a floor of 0, so **no check in the spec can distinguish
`Math.max(0, ...)` from `Math.max(loadValue, ...)`.** The two are indistinguishable on this subject. A
test that cannot separate the general answer from the special case does not license a claim about the
general answer, and this one was generated by a rule I wrote.

**What would settle it:** the same addition on a page whose load value is not zero. That case does not
exist yet, and until it runs, "decrements with a floor at the load value" is demonstrated only for a load
value of zero.

## The accumulation held, which is the point of the experiment

Addition 2's protected set was addition 1's **entire** requested play - the original program's behaviour
plus addition 1's reset. **All 7 carried-forward checks passed on every one of the four attempts**,
including the three that failed to implement the floor. Nothing earlier was given up to buy the new
feature, and nothing needed restoring.

**What that agreement is worth, stated narrowly.** It means **no contradiction was detected by these two
rules on the traces exercised.** It is not a finding that the additions are correct, and the rules are
heuristics with known holes in both directions:

    different states CAN legitimately look identical - a hidden flag, an off-screen object, an inventory
      count that is not drawn
    the same state CAN legitimately look different - an animation frame, a cursor, any visual state the
      accessor does not report
    consistent pixels can still depict the WRONG RESULT - a program that always draws the wrong score
      while reporting the expected one satisfies both rules perfectly

**Coverage is now counted per rule** rather than jointly, because two distinct states do not exercise "a
revisited state renders the same way" - that needs a state to be seen twice. An earlier version counted
two distinct states as coverage for both rules, crediting a rule that had never run.

## A USER-VISIBLE DEFECT, found after the fact by the second observation channel

**SEQ-1's results above are unchanged by this. It is an additional finding, not a revision.**

The page's canvas is **200 pixels wide**, and it draws `Player B` at `canvas.width - 110` = x 90 while
`Player A` starts at x 10. Measured by painting each label alone and masking its ink:

    "Player A: 0" at x=10    painted columns 11..107, 679 pixels inked
    "Player B: 0" at x=90    painted columns 91..187, 694 pixels inked
    PIXELS PAINTED BY BOTH   64

**64 pixels are inked by both labels: the two scores visibly collide.** This was confirmed from painted
pixels, not from `measureText`. Advance widths are the wrong instrument for the question - they include
side bearings and exclude overhanging ink, so two advance spans can overlap with nothing painted twice and
two that do not overlap can still collide. The advance metric said "overlap" here and so did the pixels,
but only the second is the claim. A screenshot of the two together is at
`legasus/out/visual/seq1-labels.png`.

**The defect is in the page as delivered by the generator**, inherited unchanged by both additions. Neither
addition introduced it and neither could have been expected to fix it - it was never in any requirement.

**Why it matters here:** every check in SEQ-1 passed, twice over, and the reported state was correct at
every step. A user looking at this scoreboard sees two overlapping numbers. That is the gap between
"passed the checker" and "the software works", found by looking at the picture rather than the state - and
it is exactly what a second observation channel is for.

**What it is NOT:** it is not a failure of the additions, not a failure of the gate at what the gate was
asked to judge, and not grounds for revising SEQ-1's verdicts. The 400-pixel layout used by the new visual
fixture is a requirement of THAT fixture and is not applied retroactively to this page.

## What this establishes

- **Established:** the frozen policy made two successive accepted additions to one program, the second
  preserving every check from the original program and from the first addition, with zero interventions and
  zero protected-set failures. **On a familiar page.**
- **Established:** the automatic feedback path works end to end on a real near-miss - a candidate that was
  right except for a boundary condition became correct after the gate's own failing-step output was fed
  back, with no human wording involved. **That is more than choosing a useful edit location: the system
  used a FAILED CHECK to guide a successful revision.**

  **It is not lasting learning, and the distinction matters.** The correction happened WITHIN one run, from
  feedback held in that run's prompt. Nothing was retained: the next task starts with the same policy, the
  same context rules and no memory that a floor was once missed. Lasting learning would mean the lesson is
  kept and successfully REUSED later - and the test for that is the third row of the table in
  MEASUREMENT-GAP-1: better results on fresh tasks with learning enabled versus disabled. No such
  comparison exists.
- **Established:** both accepted artefacts survive an independent rebuild-and-rerun, and neither
  contradicts its own rendering on the traces exercised.

## What this does NOT establish

- **Not transfer.** The page is a development page and is now doubly so.
- **Not that the software is CORRECT.** Two sources of evidence agree; both read the same state seam for
  the primary judgement, and the second only looks for internal contradictions. **A third look - at the
  picture - found a user-visible defect that both of them passed** (see above). For this page the stronger,
  task-specific requirement is that the displayed totals match the expected totals once rendering has
  settled; the checker for that now exists and this page is outside its supported layout.
- **Not reproducible generation.** Addition 1 succeeded on its first seed; addition 2 needed a second round
  after three identical near-misses. Both were single successes and neither was repeated.
- **Not a third addition.** Whether this keeps working as features accumulate is untested beyond two.
- **Not a general floor.** The accepted code hardcodes 0 and the checks could not have caught that, because
  the load value is also 0. See the section above.
- **Not lasting learning.** The within-run correction is not a retained lesson; nothing carries to the next
  task.
- **Not that the gate is sound.** The deceptive page would still be ACCEPTED by a live run: acceptance
  consults the state seam alone, and the render check is a post-hoc reading that nothing is wired to.
